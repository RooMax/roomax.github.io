The six RLS mistakes AI builders make

Each one has a policy in the kit that fixes it, a test that proves it, and an audit finding that catches it.

RLS on, no policies

Every query returns nothing. Builders "fix" it by turning RLS off, which is the next mistake.

using (true)

The same as no security. Every user's data is readable with the public key.

Writes without with check

Users can insert rows that belong to someone else, or re-point their row at another user.

Policies that query another RLS table

Recursion errors, or a silent empty result that locks everyone out.

Service-role key in the browser

It bypasses RLS entirely. Once it's in page source, anyone owns the database.

Public storage bucket "for now"

User documents become world-readable URLs and nobody revisits it.

Questions

Does it work with a Lovable, Bolt or v0 project?

Yes. Those tools create a standard Supabase project. Apply the migrations through the SQL editor or the CLI, and replace the generated client files with the ones in the kit.

Does it work with Prisma or Drizzle?

The SQL is plain Postgres and works with any tool. The TypeScript clients are for the Supabase JS SDK; a Drizzle variant is planned for buyers.

Do I need Docker?

No. The tests run against any Supabase project, including a free hosted one. Local Supabase via Docker is supported but optional.

Why revoke grants from anon if RLS is already on?

RLS filters rows. Grants decide whether the role can query the table at all. Both layers on is defence in depth, and the audit script checks both.
